# 为什么使用 TCP 443 反向隧道

## 现场背景

在一个上海电信家庭宽带环境中，对相同 VPS、相同协议和相近时间段做对照测试时，普通目标端口的持续上传吞吐明显下降，而 TCP 443 上的加密连接仍能保持较高吞吐。远程 Jellyfin 的码率超过实际可用上行后，表现为缓冲、拖动等待和起播慢。

因此本项目选择让家庭端主动连接 VPS 的 TCP 443，再在这条连接里承载两个 SSH 远端转发。

## 不应过度推断

- 这是现场观察，不是对运营商策略的官方结论；
- 端口、协议特征、目的网络、拥塞和测试方法都可能影响结果；
- 443 在其他线路上未必更快，也可能受到同样限制；
- 不应把 Speedtest 结果直接等同于真实 Jellyfin 长连接吞吐。

建议用 `iperf3` 或等价工具，在相同 VPS 上分别测试多个目标端口，并至少持续 10 分钟。若差异不能稳定复现，就没有必要把 SSH 移到 443。

## 443 的角色

```text
家庭 NAS --主动发起 SSH/TLS 类加密连接--> VPS:443
```

反向转发建立后，VPS 只在回环地址得到 `18096`、`18097`。这不等于把家庭 Jellyfin 直接公开到 443。

## 端口冲突

同一 IP、同一协议的 TCP 443 同一时刻只能被一个监听者占用。可选方案：

1. VPS 有多个公网 IP：SSH 和 HTTPS 各绑定一个 IP 的 443；
2. 用经过审计的四层协议分流器区分 SSH 与 TLS；
3. SSH 使用 443，公网 Jellyfin HTTPS 使用 8443；
4. 公网 HTTPS 使用 443，SSH 改用经过实测仍有吞吐的其他端口。

不要把 OpenSSH 私钥、主机地址或真实转发参数提交到 GitHub。
